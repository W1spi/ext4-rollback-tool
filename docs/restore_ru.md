# Восстановление (Restore process)

В этом документе описано, как работает процесс восстановления системы из снапшота, какие гарантии он даёт и какие риски необходимо учитывать.

Restore — это наиболее критичная операция во всём инструменте, так как она напрямую изменяет текущее состояние системы.

---

## Общая идея

Процесс восстановления представляет собой обратную операцию к созданию снапшота.

Если snapshot фиксирует состояние системы в определённый момент времени, то restore:

приводит текущую файловую систему к состоянию выбранного снапшота.

Это достигается с помощью rsync, который синхронизирует:

- источник → снапшот
- назначение → текущая система (/)

---

### Что происходит во время restore

rsync проходит по всем файлам снапшота и текущей системы и применяет следующие правила:

- файлы из снапшота копируются в систему
- изменённые файлы перезаписываются
- отсутствующие в снапшоте файлы удаляются (--delete)

Таким образом текущая система становится максимально близкой к состоянию снапшота.

---

## Важное поведение --delete

Флаг --delete означает:

- все файлы, которых нет в снапшоте, будут удалены из текущей системы

Это необходимо для настоящего rollback, но также делает операцию потенциально опасной.

---

## Выбор снапшота

Restore может выполняться:

- из конкретного снапшота
- из LATEST

---

## Dry-run (предпросмотр)

Перед выполнением restore рекомендуется использовать dry-run

Это покажет:

- какие файлы будут изменены
- какие будут удалены
- какие будут добавлены

---

## Ментальная модель

Restore — это не отмена изменений, а полная синхронизация системы со снапшотом.

Все изменения после snapshot будут потеряны.

---

## Гарантии

System snapshot гарантирует:

- восстановление системной конфигурации
- восстановление структуры файловой системы
- восстановление установленных компонентов и сервисов (в рамках сохранённых файлов)

Docker snapshot гарантирует:

- восстановление конфигурации docker-инфраструктуры
- восстановление структуры проектов
- возможность пересоздания контейнеров из конфигурации

---

## Что не гарантируется

- сохранение runtime-состояния системы
- корректное состояние запущенных процессов
- целостность активно изменяемых данных (например, баз данных) во время snapshot'а
- сохранение данных docker volumes и container runtime

---

## Когда возможны проблемы

Снапшоты могут давать неожиданный результат в следующих сценариях:

- база данных активно записывается во время snapshot'а
- контейнеры интенсивно изменяют данные
- выполняется обновление системы во время snapshot'а
- происходят массовые изменения файлов (например, деплой)

В таких случаях возможна частичная несогласованность данных на уровне приложения.

---

## Практические рекомендации

- остановить сервисы
- использовать dry-run
- выполнять от root
- иметь backup

---

## Ограничения подхода

- нет атомарности на уровне всей системы
- нет защиты от аппаратных сбоев
- нет встроенной истории изменений (как в backup-системах)

---

## Итог

Restore — мощный инструмент rollback.

Главное правило:

всегда понимать, какие данные будут потеряны.
