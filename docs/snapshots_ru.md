# Снапшоты

В этом документе описано, как именно реализованы снапшоты в ext4-rollback-tool:  
как они создаются, как хранятся, какие гарантии дают и какие ограничения имеют.

Основная цель — дать полное понимание механики, чтобы поведение системы было максимально предсказуемым.

---

## Общая идея

Снапшоты в ext4-rollback-tool реализованы без использования специализированных файловых систем (Btrfs, ZFS) или LVM.

Вместо этого используется комбинация:

- `rsync`
- дедупликации через hardlink (`--link-dest`)

Каждый снапшот выглядит как **полная копия файловой системы**, но фактически хранит только изменения.

Это достигается следующим образом:

- неизменённые файлы не копируются, а ссылаются на предыдущий снапшот через hardlink
- изменённые файлы копируются физически
- удалённые файлы фиксируются через механизм `--delete`

В результате:

- снапшоты создаются быстро
- дисковое пространство используется эффективно
- структура остаётся полностью прозрачной

---

## Как создаётся снапшот

Создание снапшота — это последовательный процесс, направленный на то, чтобы избежать частично записанных состояний и обеспечить предсказуемость.

### 1. Создание временной директории

Перед началом создаётся временная директория:

```
.tmp-YYYY-MM-DD_HH-MM-SS
```

Это нужно для двух вещей:

- не допустить появления “битого” снапшота, если процесс прервётся
- изолировать процесс создания до его полного завершения

Пока снапшот не готов, он не виден системе как полноценный.

---

### 2. Выполнение rsync

Основная операция:

```
rsync -a --delete --link-dest=PREVIOUS_SNAPSHOT SRC DEST
```

Здесь происходит вся логика сравнения.

rsync анализирует:

- текущее состояние системы (SRC)
- предыдущий снапшот (через `--link-dest`)

И применяет следующие правила:

- если файл не изменился → создаётся hardlink
- если файл изменился → он копируется
- если файл удалён → он будет удалён в новом снапшоте

Важно понимать:

> rsync работает на уровне файлов, а не блоков, поэтому изменения определяются по метаданным и содержимому файла.

---

### 3. Завершение снапшота

После успешного выполнения rsync:

- временная директория переименовывается в финальную:

```
YYYY-MM-DD_HH-MM-SS
```

Это делает снапшот “атомарным” с точки зрения пользователя:

- либо его нет
- либо он полностью готов

---

### 4. Обновление LATEST

После создания снапшота обновляется симлинк:

```
LATEST → последний снапшот
```

Это позволяет:

- быстро обращаться к последнему состоянию
- использовать его по умолчанию в restore
- упростить автоматизацию

---

## Как устроено хранение

Снапшоты хранятся как обычные директории:

```
.infra_snapshots/
├── system/
│   ├── 2026-04-01_00-30-00/
│   ├── 2026-04-02_00-30-00/
│   └── LATEST
```

Каждый снапшот:

- имеет полный набор файлов
- повторяет структуру файловой системы
- не требует специальных инструментов для просмотра

Это важно:

> снапшоты можно открыть обычным `cd` и изучить как обычную систему

---

## Дедупликация через hardlink

Ключевая часть механики — использование hardlink.

### Что это означает

Hardlink — это ссылка на один и тот же inode в файловой системе.

Это значит:

- файл физически хранится один раз
- но может быть доступен по разным путям

### Пример

Если файл не изменился:

```
snapshot_1/etc/config.yml
snapshot_2/etc/config.yml
```

Оба файла будут ссылаться на один и тот же inode.

---

### Почему это важно

Это даёт:

- отсутствие дублирования данных
- минимальный рост занимаемого места
- быстрый доступ к любому снапшоту

---

## Разделение снапшотов: system и docker

Снапшоты разделены на два типа:

### System

System-снапшот строится от корня файловой системы (`/`), но не сохраняет её целиком без исключений.  
Его задача — зафиксировать именно **системное состояние**, необходимое для rollback ОС, конфигурации и инфраструктурно важных компонентов.

В snapshot входят системные файлы, конфигурация, установленные компоненты и прочие данные, влияющие на рабочее состояние системы.  
При этом из него намеренно исключаются директории, которые относятся к runtime-состоянию, временным данным, кэшу, внешним точкам монтирования или пользовательским данным, которые должны резервироваться отдельно.

Не включаются:

- `/proc`
- `/sys`
- `/dev`
- `/run`
- `/tmp`
- `/var/cache`
- `/mnt/*`
- `/media/*`
- `/mnt/nextcloud_data/*`
- `/var/lib/docker/*`

---

### Docker

Docker-снапшот предназначен не для полного копирования всей docker-среды, а для сохранения **инфраструктурной части**, необходимой для быстрого восстановления сервисов.

Обычно в него входят:

- конфигурация Docker daemon (`/etc/docker`)
- директории docker-проектов (например, `/opt/devteam/docker`)
- файлы описания окружения:
  - `docker-compose.yml`
  - `.env`
  - конфиги сервисов и связанные инфраструктурные файлы

При этом docker snapshot намеренно не включает runtime-данные контейнеров и пользовательские данные, хранящиеся внутри docker storage.

Не включаются:

- `/var/lib/docker/*`
- volumes
- слои образов
- файловые системы контейнеров

---

## Ментальная модель

Snapshot — это не мгновенная фотография системы в один момент времени.  
Это согласованная файловая копия, которая формируется в течение выполнения rsync.

Это означает, что:

- данные читаются последовательно
- система может изменяться во время snapshot'а
- итоговое состояние является консистентным на уровне файлов, но не обязательно на уровне всей системы в конкретный момент времени

---

## Гарантии

System snapshot гарантирует:

- восстановление системной конфигурации
- восстановление структуры файловой системы
- восстановление установленных компонентов и сервисов (в рамках сохранённых файлов)

Docker snapshot гарантирует:

- восстановление конфигурации docker-инфраструктуры
- восстановление структуры проектов
- возможность пересоздания контейнеров из конфигурации

---

## Что не гарантируется

- сохранение runtime-состояния системы
- корректное состояние запущенных процессов
- целостность активно изменяемых данных (например, баз данных) во время snapshot'а
- сохранение данных docker volumes и container runtime

---

## Когда возможны проблемы

Снапшоты могут давать неожиданный результат в следующих сценариях:

- база данных активно записывается во время snapshot'а
- контейнеры интенсивно изменяют данные
- выполняется обновление системы во время snapshot'а
- происходят массовые изменения файлов (например, деплой)

В таких случаях возможна частичная несогласованность данных на уровне приложения.

---

## Ограничения подхода

- нет атомарности на уровне всей системы
- нет защиты от аппаратных сбоев
- нет встроенной истории изменений (как в backup-системах)

---

## Практические рекомендации

Чтобы получать максимальную надёжность:

- запускать снапшоты в периоды низкой активности
- при необходимости останавливать критичные сервисы (например, базы данных)
- хранить снапшоты на отдельном диске (если возможно)
- контролировать `KEEP_COUNT`
- не использовать snapshot как замену полноценному backup

---

## Итог

Снапшоты в ext4-rollback-tool — это:

- простой механизм без скрытых слоёв
- полностью прозрачная структура
- высокая скорость работы
- эффективное использование диска

Главное преимущество подхода:

> предсказуемость и контроль вместо “магии” файловых систем
